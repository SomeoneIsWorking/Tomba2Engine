## Claim

This port called BIOS InitHeap with a1=0 for its whole life — a ZERO-capacity heap — and it was latent only because a 428-frame boot makes zero BIOS malloc calls

## Evidence

TWO HALVES, WITH DIFFERENT STRENGTHS — read them separately. (1) THE MECHANISM, re-checked from source by this session: `git -C $PSX/psxport show 726d10c9^:runtime/recomp/native_boot.cpp` shows the old crt0_setup assigning c->r[28], c->r[29], c->r[30] and `c->r[4] = a0 + 4`, then `rec_dispatch(c, cfg->libcInit)` — c->r[5] is never assigned anywhere in the function. Tomba!2's libcInit 0x80089860 IS the BIOS A(39h) InitHeap(ptr,size) thunk and the guest's own crt0 has a1 live at that jal (crt0_extract over MAIN.EXE: 'a1 live at the call: YES'), and hle.cpp case 0x39 copies a1 into Hle::heap_size and blk[0].size, which heapAlloc treats as the arena's capacity. So the arena was created with capacity = whatever r[5] held. (2) THE VALUE, measured by the framework session that landed 726d10c9 on a REAL headless boot of this port and NOT re-run by the session recording this claim: the new crt0 log line (native_boot.cpp:257) reported 'a1 held 0x00000000 = 0 before crt0 set it'. WHY IT NEVER SHOWED: a 428-frame boot (attract + newgame + 401 frames) made ZERO BIOS malloc calls, so the 0-byte arena was never asked for anything. The new Hle::heap_refused counter read 0 on that run — and that is 0 refusals of 0 REQUESTS, which is not evidence that the heap works. Fixed in 726d10c9: crt0_apply sets r[5] = heapsz (Tomba!2's real value 0xF99D0).

## What would falsify it

**THE VALUE.** The falsifier this section originally named — "a run of this port at psxport 726d10c9^ that logs a1 != 0 at the libcInit dispatch" — is CORRECTED because it is NOT EXECUTABLE: the log line that reports a1 was ADDED by 726d10c9, so no run at 726d10c9^ can print it, and a falsifier nobody can run is a belief. The executable test is on the CURRENT build and needs no revert: `crt0_apply` logs the register content it is about to OVERWRITE, so `PSXPORT_NOPACE=1 python3 tools/gate.py boot --frames 400` printing `libcInit 0x80089860: … (a1 held 0x????????  … before crt0 set it)` with a NON-ZERO value falsifies the measured value. That pre-crt0 `r[5]` IS what the pre-726d10c9 `crt0_setup` passed as the capacity, because that code assigned `r[4]` and never `r[5]`. Not guaranteed by construction — `r[5]` is whatever a freshly allocated `Game` holds — so it is a MEASUREMENT that must keep reproducing, and it has (twice, on two different binaries: md5 `4e21d132…` and md5 `32fcc50002dd`).

**THE LATENCY**, and this is where the original evidence was WEAKEST: it asserted "zero BIOS malloc calls" while naming no instrument, i.e. a negative from a method that could not have shown the positive. The instrument is `PSXPORT_DEBUG=bios` — `Hle::dispatchBios` logs EVERY BIOS call on that channel, handled or not, before the switch. So the falsifier is: run the same gate with `PSXPORT_DEBUG=bios` and grep the log for `A0:0x33` / `A0:0x37` / `A0:0x38`; any hit falsifies the latency half, because it means the 0-byte arena WAS asked for memory and something silently got NULL. The channel must be validated in the same run by its POSITIVE CONTROL — `A0:0x39` (InitHeap) MUST appear, since the boot demonstrably calls it; a log with no `A0:0x39` means the channel did not fire and the zero says nothing. Denominators to state alongside any such run: total `[bios]` lines, and the full per-function A0-table census (measured: 294 lines, 6 A0 calls, 0 of them allocations).

**THE MECHANISM** half is falsified only by showing `crt0_setup` was not on this port's boot path.

**BLIND SPOT this claim does NOT cover:** the latency measurement is one 428-frame attract+newgame boot in seaside/mode-0 content. "Zero mallocs" is a statement about THAT run, not about the game — a later stage that does allocate is exactly where a wrong `heap_size` would finally bite.

## Re-confirmed 2026-08-12 21:13:38

(2) THE LATENCY is now measured WITH A DENOMINATOR AND A POSITIVE CONTROL, by the instrument that can show the other answer: PSXPORT_DEBUG=bios logs EVERY BIOS call handled or not (hle.cpp::dispatchBios, unconditional lucent::debug on the "bios" channel). Same gate, same 428-frame boot, PSXPORT_DEBUG=bios (env audit AT EXIT: 5 set, 0 UNKNOWN, so the channel was really read) -> scratch/logs/gate-boot-20260812-211111.log, 294 [bios] lines. Full A0-table census: A0:0x44 x2, A0:0x72 x1, A0:0x70 x1, A0:0x49 x1, A0:0x39 x1 -- SIX A0 calls total. grep -c for A0:0x33 (malloc) / A0:0x37 (calloc) / A0:0x38 (realloc) = 0. So 0 of 294 logged BIOS calls, and 0 of 6 A0-table calls, were an allocation.
BLIND SPOT this measurement does NOT cover: it is one 428-frame attract+newgame boot in seaside/mode-0 content. It says nothing about later stages, and any stage that DOES malloc is where a wrong heap_size would have bitten.
