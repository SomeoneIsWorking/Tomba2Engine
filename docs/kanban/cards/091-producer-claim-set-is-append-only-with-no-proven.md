Found 2026-08-12 while closing #88, which it is NOT a duplicate of: #88 was prims keying at a submit leaf; this is the claim set being unable to retire a claim.

THE MECHANISM. psxport runtime/recomp/producer_census.h::appendClaims() appends unconditionally and its own comment states the rationale: 'append-only; a claim earned by a native producer drawing is never un-earned by a later leg that skips it'. That rationale is CORRECT for the case it names — a guest leg does not run native producers, so absence on one leg must not retire a claim. It does NOT cover the case that actually occurred: **the producer's KEY moved because the CODE changed.** Nothing in the file records which build earned which address, so a live claim and a fossil are indistinguishable.

THE OBSERVATION THAT EXPOSED IT. Two native-leg runs, both 298 frames, both exactly 152,981 prims — the same workload — keyed at DIFFERENT addresses:
  run-2026-08-11T23:57:38.jsonl -> 0x800803DC  prims_native 152981  frames 298
  run-2026-08-12T13:16:14.jsonl -> 0x80146478  prims_native 152981  frames 298
9c94008 ('key perObjFlush's world prims by the per-mode emitter', 2026-08-12 00:12:21) sits between them and is what moved the key: it introduced Render::resolvePerModeEmitter and keyed the scope on the resolved per-mode emitter, where 0x800803DC is only the GENERIC_EMITTER fallback (perobj_dispatch.cpp:118). Both addresses are legitimate producers with curated docs (docs/producers/0x800803DC.md, docs/producers/0x80146478.md), which is exactly why neither looks wrong in isolation.

WHY IT MATTERS — it manufactures a false negative, the worst kind here. claims.txt currently holds 106 lines for 10 distinct addresses (append-only, so one block per run). If an address in that set is no longer earnable by the present build, the guest leg still resolves to it — run-2026-08-12T11:48:15.jsonl resolves 107,066 guest prims to 0x800803DC with prims_native 0. A reader of the DB sees 'guest prims, no native producer' and concludes an effect is unported, when the native producer may exist under the key it moved to. That is the DB asserting a negative its method cannot support.

**ESTABLISHED 2026-08-12 (was "NOT ESTABLISHED"): `0x800803DC` IS STILL EARNABLE BY THE PRESENT BUILD. It is NOT a fossil, and the card's own suspicion is REFUTED — measured, in both directions, on the built binary at HEAD 11a75fb.** Do not prune it.

Its `prims_native: 0` there is the structural fact `loadClaims`' own banner states (no single leg runs both halves), not a claim of "unported".

SO THE FOSSIL IS THE **PROVENANCE**, NOT THE ADDRESS — and the card's mechanism stands, with a sharper diagnosis. The claim on disk was not earned by observing a generic-mode area: the 23:57:38 run predates 9c94008, which ADDED `perObjFlush`'s scope, and its own commit message records that the draft's routing recorder "was dead by construction", so that leg keyed ALL world prims generically. The 23:57 key was the degenerate fallback.

THE SECOND DEFECT, found while measuring and worth as much as the first: **`appendClaims` re-emits the LOADED set, not what the run earned.** `mClaims` is populated by `loadClaims` at begin and appended verbatim at finish, so every run writes a full copy of the file's own contents. That is why `0x800803DC` appears in the NEWEST block of `scratch/producers/claims.txt` (7 of 106 lines) while no run since 9c94008 earned it: the newest block always looks freshly earned. It also means the on-disk file cannot answer "what did this run earn" even in principle — hence the per-leg `PRODUCERS_DIR` above, which is the only way to get an honest earned-set out of the present runtime.

DIAGNOSTIC LANDED (game side, available now): **`tools/producers.py stale`** reconstructs per-claim provenance from the run corpus — the per-run JSONL is NOT union-echoed, so a row with `prims_native > 0` is a real EARN event and "when was this claim last earned" is a query. Reference = the newest commit over the union of two sets: the game paths that open a `ProducerScope`, plus the FRAMEWORK's own census/scope files dated by the SUBMODULE's history (not by the gitlink — a docs-only framework commit must not fossilise anything, and dating by the pin made the whole corpus refuse when 11a75fb bumped psxport for 2 docs files). A claim is credited only to a leg whose RECORDED binary md5 equals the present build's. Full instrument card, with the both-directions real-data validation and the sabotage proof: `docs/info/instruments/049-tools-producers-py-stale-reconstructs-per-claim.md`. Its negative deliberately says NOT-RE-EARNED, never DEAD, and prints the blind spot this card measured: a claim goes un-earned whenever the corpus never visited the content that earns it.

**AND THE TOOL'S CORE ASSUMPTION, WHICH WAS UNSTATED AND FAILED IN EXACTLY THE CASE THIS CARD EXISTS FOR.** `stale` dated a RUN's wall clock against a COMMIT's time, silently assuming "the run happened after the commit, therefore the binary was built from it". Nothing checked that, so a run of a STALE or DIRTY binary started after a key-path commit was credited as re-earning every claim it touched — a genuine fossil read green. Fixed by making the artifact an input: the built binary must be newer than every key-deciding path (else exit 2), an uncommitted key-path edit raises the reference to that edit's mtime, and an earn is credited only to a leg whose `binary.txt` md5 (written by `tools/gate.py` before AND after the run) equals the present binary's. That produces a THIRD state — BUILD PROVENANCE UNKNOWN — because mtime cannot identify the binary a past run used, and calling those runs re-earned is the false negative while calling them fossils is a different lie. RESIDUAL, stated rather than hidden: an md5 recorded at launch is a real identity but `touch` fakes an mtime and nothing here can say which `PSXPORT_DIR` a build came from — which is what fix step 2 below (`PSXPORT_BUILD_ID` from `git describe --always --dirty`, emitted into every run's JSONL) finally settles.

FIX (framework, psxport — HANDOVER, this session did not own that tree). Three changes, in this order, all in `runtime/recomp/producer_census.h` + `producer_db.cpp`. The measurement above is what makes each one specific rather than a guess.

1. **SEPARATE "earned this run" FROM "loaded from disk", which the runtime currently cannot distinguish.** `ProducerCensus::note()` adds to the same `mClaims[]` array that `loadClaims` filled, so `claimCount()` is a union and `appendClaims` writes the union. Add a parallel `bool mClaimEarnedHere[CLAIM_CAP]` set only on the `note()` path (native push on a GUEST key), and have `appendClaims` write BOTH facts per line. Without this step no provenance is recordable at all, and the diagnostic below has nothing to report.

2. **Per-claim PROVENANCE in the file, keeping it append-only and keeping the bare-`0x…` reader working.** Line format `0x800803DC <run-stamp> <build-id>`; `loadClaims`'s existing `line[0]=='0'` branch already `strtoul`s the address and ignores the tail, so an old file still loads and a new file loads in an old build. `<build-id>` must be a real code identity, not a timestamp — psxport has NO build stamp today (no `GIT_*`/`BUILD_ID`/`__DATE__` anywhere in its CMake or runtime), so add one: a `PSXPORT_BUILD_ID` compile definition from `git describe --always --dirty` in psxport's CMakeLists, exposed as a `TextVar` so it also lands in the JSONL and in the env audit. `--dirty` matters here: the fossil in this very card was created by an UNCOMMITTED draft, and a clean-sha-only stamp would have recorded it as if it were 9c94008's predecessor.

3. **The LOUD report from `producer_db_finish`, with the negative designed first.** For each claim in the loaded set, compare its recorded build-id against this run's; print unconditionally, with denominators:
   `claim set provenance: N of M claim(s) were last earned by a DIFFERENT build (<id>), K by this build (<id>), P carry no provenance (written by a pre-provenance build). Attribution of guest prims to the N is possibly a FOSSIL of a producer key that MOVED.`
   And it must state the blind spot, because this card proves that omitting it produces exactly the wrong conclusion: **not re-earned is NOT dead.** A producer key is a function of guest state — `perObjFlush`'s key is the per-mode emitter the area's render-mode byte selects, and 12 of 22 modes select `0x800803DC` — so a claim goes un-earned whenever the run never visited the content that earns it. The line must therefore say "no run of this build has re-earned these; reach the content before treating any as dead", never "these are stale". A `--selftest`-equivalent (psxport has `tests/test_producer_census.cpp`) must gate both classes: one claim re-earned this build, one carrying a foreign build-id, and assert the report names the second and not the first.

DO NOT prune, and do not make absence retire a claim — the existing append-only comment is right for the reason it gives, and this card is the second reason: the address it looked safest to prune is live in 12 of 22 areas.
