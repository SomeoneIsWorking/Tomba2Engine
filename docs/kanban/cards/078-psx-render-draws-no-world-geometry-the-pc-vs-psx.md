CONSEQUENCE, and this is the point: any conclusion of the form 'psx_render does not draw X, therefore vanilla culls X' is VOID in this build — psx_render does not draw ANY world geometry, so it cannot produce the failing answer. docs/gfx-debug.md already says 'there is no render oracle'; this is the measurement behind that sentence and it needs to be in the doc as a number.
LIKELY CAUSE (not verified): kanban #45's campaign retired the substrate-GTE projection producers, so the guest OT is no longer filled with the world. If so psx_render is not repairable-by-accident and every doc/tool that offers it as a reference (tools/warpsweep.sh, docs/areas.md, the gfx-debug playbook) is offering a dead instrument.

**2026-08-06:** ROOT-CAUSED AND FIXED 2026-08-06. The suspected cause (kanban #45 retired the substrate-GTE producers, so the OT is empty) is REFUTED by measurement: 'debug otattr' + REPL 'otattr' re-walked the last-walked OT on the psx leg at area 0 f3103 and found 983 packets — 352 op=0x7C 16x16 sprites, 308 GT3, 298 GT4 — with plausible screen coords, and BOTH legs report identical spans=15668/gteBuckets=15. The OT was full; the picture was not.
REAL CAUSE: the OT walk does not paint in OT order. gpu_dma2_linked_list hands every decoded packet to the NATIVE RenderQueue, which re-bands it (gpu_native.cpp:874/:1036, layer = is3d ? RQ_WORLD : (bg ? RQ_BACKGROUND : RQ_HUD), painted low->high). A 16x16 sprite is 'bg' only via node_is_bg / sprite_is_bg_texpage provenance or bg_2d's >=3/4-screen coverage test. sprite_is_bg_texpage reads GpuState::s_bgtp_*, published by gpu_bg_texpage_set — whose ONLY caller was Render::backdropRender, a pc_render producer reached from renderScene(), i.e. only from the pc_render arm of Engine::drawOTag. psx_render returns before renderScene, so on the reference leg the backdrop atlas page was NEVER published. PSXPORT_PRIMDUMP=3100:3102, area 0 f3100: 972 prims = 617 is3d=1 world polys + 355 sprites, 355/355 with bg=0, 352 of them the 16x16 tiles of texpage (896,0). All 352 landed in RQ_HUD (topmost band) and painted over the world the substrate had just drawn.
FIX (game side): Render::backdropTexpagePublishTick(), called from Engine::drawOTag right after areaCacheTrustTick() and BEFORE the render-mode branch; the two publishes inside backdropRender are deleted (one publisher). Identical defect and identical fix shape to kanban #41.
EVIDENCE + NEGATIVE CONTROL, headless, one boot per leg, recipe newgame/skip 3000/run 60/run 2/shot with PSXPORT_GATE=1 PSXPORT_NO_FMV=1 PSXPORT_NOAUDIO=1 PSXPORT_NOPACE=1: BEFORE scratch/shots/psxref/a0_psx.png = sea and sky only; AFTER scratch/shots/psxref/a0_psx_fix.png = village, hut, Tomba, terrain, fence, crane, gem. In-band leg signal (not the measured pixels): PSXPORT_DEBUG=bgtp prints 3098 'tilemap=1 tp=(896,0)' lines on the fixed binary and the channel does not exist on the old one; the primdump flips 352/352 tiles bg=0 -> bg=1 with the 3 HUD sprites still bg=0.
PSXPORT_ORACLE=1 was unaffected by this specific banding bug because it forces pure OT painter order, so no native band/depth decision can touch the picture. Verified a0/a13/a14 all draw the full world and sit at the documented ~28k >8/255 pc-vs-psx baseline (28794/28238/28171 of 76800); ORACLE vs ORACLE+PAINTER differs by 13/76800. This proves it is useful for ordering diagnostics only. Health-wheel #22 later proved it shares host shader semantics and can match the native path while both are wrong, so instrument I044 is distrusted as a correctness reference; use I051/I053 within their declared scopes.
