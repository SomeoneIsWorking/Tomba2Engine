Measured 2026-07-23 while closing #26 (area 12, replay seesaw-weight). 'renderpsx on' issued at f3621 then 'run 1' + shot gives a frame BIT-IDENTICAL (0/76800) to the pure-pc f3622, even though the flag reads back 1 ([repl] Render::psxRender = 1). Issuing the SAME command BEFORE 'warp 12' gives a frame bit-identical (0/76800) to the boot-PSXPORT_RENDER_PSX=1 frame, and 23091 px from the pc frame. So the switch latches at scene entry.

CONSEQUENCE: ground truth #1 in docs/gfx-debug.md (the in-process toggle) silently returns a pc frame when flipped inside a loaded area. Combined with the bare-'renderpsx'-is-a-no-op defect (fixed), this is what manufactured #26 — see docs/findings/render.md. Until this is root-caused, any renderer A/B must take its reference from a SECOND RUN with PSXPORT_RENDER_PSX=1 at boot (tools/warpsweep.sh does that).

NOT root-caused: Engine::drawOTag (game/game_tomba2.cpp) branches on c->rsub.mode.psxRender() every frame, so something upstream must latch per scene entry. Note findings/render.md records the toggle DID change the picture mid-scene in other contexts (#14 mace spikes, the 'run 2 after toggling' rule), so the latch may be specific to what a warp reloads — that is the thing to pin down.

**2026-07-23:** 2026-07-23 ROOT-CAUSE CHAIN NARROWED to one function (operator, from code reading — not yet fixed). (1) REPL  ALWAYS reads the VK target via gpu_vk_shot (gpu_vk_enabled() is always 1 — repl.cpp:198), never the software s_vram. (2) drawOTag (game_tomba2.cpp:164) branches live on psxRender() every frame: psx branch rasterizes the guest OT into s_vram (gpu_dma2_linked_list) and does NOT call renderScene(), so the NATIVE GEOMETRY BATCH is empty; pc branch calls renderScene() which fills the batch. (3) present_window()->blit_src(s_vram)->gpu_vk_present() both UPLOADS s_vram AND renders the native batch into the VK target. So the latch lives in gpu_vk_present's upload_vram + render_geom interaction: this is the SAME mechanism as kanban #20 (render_geom CLEARS s_vram_tex to black when the batch is empty). NEXT SESSION: read gpu_vk_present / render_geom in external/psxport/runtime/recomp/gpu_vk.cpp and determine, with an empty batch (psxRender mode), whether the uploaded s_vram survives to the VK target or is clobbered, and whether that decision reads the LIVE psxRender flag or a value latched at scene entry. Likely fix: in psxRender mode present the uploaded s_vram (skip the empty-batch clear), keyed on the live flag. This is a present-path fix (#20 sibling), do it deliberately with fps60dump/shot A/B, not a rushed edit. Until fixed, ground-truth #1 protocol stays: take the psx reference from a SECOND boot run with PSXPORT_RENDER_PSX=1 (tools/warpsweep.sh / render_cmp.py already do).

**2026-07-23:** 2026-07-23 CORRECTION — my earlier hypothesis is FALSIFIED, and one mechanism is now RULED OUT (progress by elimination). I previously wrote that the latch was gpu_vk_present/render_geom's empty-batch clear (the kanban #20 mechanism). That is WRONG. Confirmed by reading the code: (a) the empty-batch clear is real and sits at external/psxport/runtime/recomp/gpu_vk.cpp:702 — 'if (total == 0)' clears s_vram_tex to black and returns, deliberately ('No native submit this frame -> the PC renderer shows BLACK, never the raw PSX VRAM'); BUT (b) in psxRender mode the batch is NOT empty, because gp0_exec TEES every rasterized primitive into the VK geometry batch (gpu_vk_draw_tritri / gpu_vk_draw_semi, gpu_native.cpp ~781-937). That tee is exactly why PSXPORT_RENDER_PSX=1 produces a picture on the VK target at all. So the empty-batch clear cannot be the latch. STILL TRUE and useful: REPL  ALWAYS reads the VK target (gpu_vk_shot; gpu_vk_enabled() is always 1), and drawOTag (game_tomba2.cpp:164) branches live on psxRender() every frame. WHAT TO INVESTIGATE NEXT, given the elimination: if the flag is live and the tee fills the batch, then a mid-scene toggle must be failing to produce OT-walked prims — i.e. the guest OT that drawOTag walks (otHead) is empty/stale on the toggled frame. Check whether the guest still BUILDS a drawable OT while pc_render is active (CLAUDE.md asserts the substrate render orchestrator runs underneath and the OT is part of byte-exact state — VERIFY that rather than trusting it), and whether the packet pool/OT is reset per frame in a way that leaves nothing to walk when the walk was skipped the previous frame. Instrument: PSXPORT_DEBUG with the gp0/vkstats channels — count teed prims on the frame after a mid-scene toggle vs after a boot-time PSXPORT_RENDER_PSX=1. A zero prim count there confirms the empty-OT theory. Until root-caused the protocol stands: take the psx reference from a SECOND boot run with PSXPORT_RENDER_PSX=1.

**2026-08-05:** 2026-08-05 ROOT-CAUSED AND FIXED — and this card's TITLE was wrong. The toggle is NOT honoured per scene entry: it is honoured every frame, with a one-PRESENT lag (a REPL `shot` runs before the next frame does, so it reads the previously presented picture — use `run 2`, not `run 1`). What was actually broken is worse than 'returns a pc frame', and only in the psx->pc direction: switching OUT of psx_render mid-scene left the picture PERMANENTLY near-black (nonblack 7627/76800, mean 8.6 vs 78.5; still black 70 frames later, and with fps60=0 too, so not an fps60/mSink mechanism).

CAUSE, measured, not inferred: the AREA-CACHE TRUST LATCHES (Render::mSceneTableTrusted / mBackdropTrusted) lived at the top of Render::sceneNative, i.e. ONLY on the pc_render branch of Engine::drawOTag. Under psx_render drawOTag returns before renderScene, so the edge detector never ran, both latches stayed at their false construction value across the narration->field handoff, and the re-zero each waits for went by unobserved. fieldEntityRender(SCENE_ENT_TABLE) and backdropRender are gated on them, so both stayed suppressed forever after a mid-scene switch to pc.

NEGATIVE CONTROL (same instrument, same mode, produced the failing answer before the change): new channel PSXPORT_DEBUG=areatrust prints both latches AND the two guest bytes they latch on. Pre-fix, toggled leg: 'sceneTable=0 backdrop=0 ent+6=132 bg+10=36'; pure-pc leg at the same point: 'sceneTable=1 backdrop=1 ent+6=132 bg+10=36' — identical guest state, opposite latch state. Independently, preseqobj counted 0 of 704 RQ_BACKGROUND items emitted on the toggled leg (RQ_WORLD 784 vs 1370).

FIX (game-side, no framework change): the latch is a state machine over GUEST state, not part of building the picture, so it is now Render::areaCacheTrustTick(), ticked once per logic frame from Engine::drawOTag BEFORE the render-mode branch, guarded to exactly the scenes whose producer calls sceneNative (Field, SopNarration, Title+s48==7 attract). game/render/render_walk.cpp + render.h + game_tomba2.cpp.

VERIFIED post-fix, AUTO_SKIP seaside area 0, headless, 320x240 = 76800 px denominator:
  psx->pc mid-scene, then compared against a pure-pc boot leg at the SAME logic frame: 0/76800 px differ (bit-identical). Pre-fix the same pair differed by 71401/76800.
  pc->psx mid-scene, 2nd frame after the command onward: 0/76800 vs a boot-time PSXPORT_RENDER_PSX=1 leg. Stays identical for the next 20 frames.
  fps60=0 leg: nonblack back to 76723-76794/76800 (was 7624-7773).
  NO REGRESSION on either boot path: pure-pc f400 shot and boot-psx f401 shot are both 0/76800 against the pre-fix binary.

NOT VERIFIED, state it rather than imply it: only ONE scene (area 0 free-roam at AUTO_SKIP f400) and only headless; not swept across areas, not tested in a window, not tested through a scene TRANSITION while toggled, and the hut-interior producer does not use these latches so it was not exercised. The one-present shot lag is measured but NOT root-caused — it is a property of when the REPL runs relative to the frame, and 'run 2' is the correct recipe either way.
